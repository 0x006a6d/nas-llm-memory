# 文書管理規程 (このシステムの運用規則)

記憶統合システムが扱う記録の一生 — **収受 → 整理 → 保存 → 起案・決裁 → 管理簿への記載 → 保存期間の満了 → 移管または廃棄 → 点検・報告** — を定める。公文書管理法と自治体の文書管理規則の構成に合わせているが、対象は行政文書ではなくこのシステムのデータであり、法的効力を持つものではない。

参考にした制度: [公文書管理法・行政文書の管理 (内閣府)](https://www8.cao.go.jp/chosei/koubun/about/shikumi/g_bun/g_bun.html) / [東京都文書管理規則](https://www.reiki.metro.tokyo.lg.jp/reiki/reiki_honbun/g101RG00000187.html)

## 第1章 総則

- **収受** — 各端末の hook と sender が送ってきたセッション記録を ingest が受け取り、`raw_payloads` と `turns` に保存すること
- **行政文書ファイル (集合物)** — 相互に関連する記録の束。このシステムでは `(大分類, 中分類 = project_key, 期間)` を 1 ファイルとする
- **管理簿** — `record_files` テーブル。ファイルの分類・名称・保存期間・満了する日・満了時の措置・保存場所・状態を記載する
- **規程** — `retention_rules` テーブル。大分類ごとの保存期間・満了時の措置・施行ゲートの正本

## 第2章 整理 (法5条相当)

収集した記録は夜間バッチの `seiri()` が毎晩整理する。

1. **分類する** — 大分類は下表のとおり。中分類は project_key、小分類はファイル名称 (例: 「収受(生ログ) demo-project 令和8年度」)
2. **期間で束ねる** — 保存期間が年単位なら年度 (4/1 区切り)、日単位なら月。日単位を年度で束ねると、その年度に行が入り続ける限り満了しないため月で締める
3. **保存期間と満了する日を設定する** — 年度起算は「作成年度の翌年度初めから N 年」= (年度+1+N)/3/31、日起算は「その月の末日から N 日」
4. **満了時の措置を決めておく (レコードスケジュール)** — 移管 / 廃棄 / 常用のいずれかを記載時に確定する

### 標準文書保存期間基準

| 大分類 | 実体 | 保存期間 | 満了時の措置 | 施行 |
|---|---|---|---|---|
| shuju-raw | raw_payloads | 90日 | 廃棄 | 決裁で施行 |
| shuju-turns | turns | 3年 | 廃棄 | 後閲印が条件 |
| shuju-memo | auto_memory_snapshots | 1年 | 廃棄 | 後閲印が条件 |
| kiroku-fact | facts | 常用 | (満了しない) | — |
| kessai-doc | drafts | 10年 | 移管 | 後閲印が条件 |
| renraku-msg | messages | 1年 | 廃棄 | 後閲印が条件 |
| unyou-run | batch_runs | 3年 | 廃棄 | 決裁で施行 |

規程は `retention_rules` が正で、`enabled` が真の分類だけを整理・廃棄の対象とする (段階適用)。どのテーブルをどう束ねるかは `batch/kanribo.py` の `SOURCES` が正で、両者の一致は `tests/test_kanribo.py` が検査する。

## 第3章 保存

- 現用の記録は NAS の PostgreSQL に置く。保存場所は管理簿の `location` に記載する
- 日次の `backup.sh` が pg_dump を `/volume1/claude-backup/pgdump/` に取る
- 秘密情報は収受の時点で正規表現マスクを掛ける (`ingest/redact_patterns.json`)

## 第4章 起案・決裁 (現用の記録に対する処分)

facts の登載、index の改定、skill の登載、廃棄、移管は、いずれも起案文書として起票し、審査 (課長) → 決裁 (部長) を経て施行する。詳細は README の「起案・決裁ワークフロー」を参照。

- **専決** — 軽易な案件は審査で決する
- **上申** — 既存記録の置換・撤回・矛盾の疑いは決裁へ回す
- **未決繰越** — 決裁が付かない案件は承認も否決もせず、翌晩に再審理する
- **後閲** — 施行後 (または施行前) に人間が確認する。差し戻すと翌晩に再審理される

## 第5章 保存期間の満了 (法5条・8条相当)

- `check_manryou()` が毎晩、満了日を過ぎた現用ファイルを **満了** に進める。ここでは何も消さない
- 満了したファイルは措置に従って処理する:
  - **廃棄** → 第6章
  - **移管** → 第7章
  - **常用** → 満了しない (facts はここに当たる)

## 第6章 廃棄 (法8条2項相当)

廃棄は取り消せない。したがって次の順を必ず守る。

1. **起案** — `ringi_haiki()` が満了ファイルごとに廃棄伺いを起票する。伺い文には件名・数量・保存期間・満了日・id 範囲・保存場所を書き、**廃棄一覧**を別記に添える
2. **審査** — 課長モデルが、満了の事実と歴史的価値の有無を見て上申または否決する
3. **決裁** — 部長モデルが承認または否決する (国の制度で内閣総理大臣の同意に当たる位置づけ)
4. **施行** — 規程の施行ゲートによる:
   - `sokujiko` — 決裁で施行する (raw_payloads・batch_runs)
   - `kouetsu` — 書庫で人間が後閲印を押して初めて施行する (turns・auto_memory・messages)
5. **施行前の確認** — 当日の pg_dump が無ければ施行しない

### 廃棄しないもの

- **現用の事実の根拠** — 現用 facts の `provenance` が指す turns は、保存期間が満了しても廃棄しない (根拠の消えた事実を残さないため)
- **収集の継続に必要な記録** — watermark を持つ最新の成功 run と実行中の run
- **受信の証跡** — raw_payloads は本文だけ廃棄し、行・受信日時・廃棄日時・決裁文書の参照は残す

## 第7章 移管 (法8条1項相当)

保存期間が満了した決裁文書 (kessai-doc) は廃棄せず移管する。移管は中身を残す措置なので審査は置かず、決裁のみとする。

1. **書き出し** — `/volume2/claude-system/archive/<年度>/<分類>_<project>_<期間>.jsonl.gz` へ 1 行 1 JSON の gzip で出す。`.tmp` へ書いて sha256 を取ってから確定名へ rename する
2. **起案** — 移管先のパス・件数・sha256 を伺い文と別記に載せる (何をどこへ移すのかを決裁者と後閲者が確認できるようにする)
3. **決裁** — 部長モデルが承認または否決する
4. **施行** — 規程の施行ゲートに従い、DB から当該範囲の行を外す。管理簿の状態を `ikan_zumi` にする

### 復元

移管したファイルは gzip を展開すれば 1 行 1 JSON で読める。列名は移管時のテーブル定義そのままなので、必要なら同じテーブルへ流し込める:

```bash
zcat /volume2/claude-system/archive/2026/kessai-doc_proj_2026.jsonl.gz | head -1 | python3 -m json.tool
```

## 第8章 点検・報告 (法9条相当)

- 毎晩、管理簿と実データの整合を点検する
- 年度替わりに管理状況報告を起票する (受入件数・廃棄件数・移管件数・未決や後閲の滞留)

## 第9章 適用の手順

1. `015_kanribo.sql` を適用する (管理簿と規程のテーブルができる。この時点では `enabled` が全て偽なので何も起きない)
2. 分類を 1 つずつ有効にする。まず `shuju-raw`:
   ```sql
   UPDATE retention_rules SET enabled = true WHERE category = 'shuju-raw';
   ```
3. 翌晩の整理で管理簿にファイルが並ぶ。dashboard の「管理簿」タブで分類・件数・満了日を確認する
4. 満了したファイルが出たら廃棄伺いが起票される。書庫で内容を確認する
5. 実績を見てから次の分類を有効にする
